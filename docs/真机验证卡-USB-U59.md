# 真机验证卡 · USB U-57…U-59（镜像 `6e34ff6f27e8`）

这一版的重点不是"又改了几行驱动"，而是**让下一次开机自己把答案写下来**。所以这次不需要拍照。

## 一句话

插上这块 U 盘开机 → 读盘 → 告诉我一声。日志会落在机器自己的 NVMe 上，我从 Windows 直接读回来。

## 为什么要这么改

上一版（`9d3bd6f317ba`）开机后仍然没有鼠标，但取证复核发现更糟的一件事：**那次开机没有留下任何文字日志**。

- U 盘 LBA 51200 → 空的（内核从未写到 U 盘，与 U 盘枚举不了同源）；
- 内盘 NVMe 日志段（头 LBA 64、文字 LBA 65 起）→ 全零，可更早的照片里明明有 `log=1 dev=nvme0 sec=45`。

原因找到了：`usblog_flush()` 写完扇区**从不调用介质的 flush**（`usblog.c`，`blkdev_t` 有 `blk_flush_fn` 钩子却没用），NVMe 把 45 个扇区留在写缓存里，电源键一按就没了。**U-59 修掉这个。**

同时补上三处"以前只存在于推理里"的证据：

- **U-57 空环探针**：把 EP0 传输环清成"除 link TRB 外没有 owned TRB"，再照常写门铃。真读过这条环的控制器**必须**报 Ring Underrun（14）或 TRB Error（5）；没读过就一声不吭。这是唯一一个不需要设备配合、就能判定"门铃有没有送到控制器"的实验。
- **U-58 门铃前后读 EP0 dequeue**：写门铃前读一次、2 ms 后再读一次。指针前移 = 控制器确实取走了 TD（问题在设备/链路）；不动 = 这条 TD 从未被取走（问题在门铃或环基址）。第一次无效会再写一次门铃复查。
- **U-58 附带**：一次开机的前 8 个事件按 `type/slot/ep/code` 逐条进日志，第一个失败的传输额外记 `portsc` 与 `usbsts`。

## 开机怎么试

1. 机器放下，插这块 U 盘，U 盘启动。
2. 等到桌面（或等 45 秒诊断页自己结束）。
3. 鼠标能动就动一下、动不了也没关系——**不用拍照**。
4. 按电源键长按关机（直接断电也行，日志现在会落盘），然后跟我说一声。

## 屏幕上会出现的新字段（想拍也行，不拍也行）

诊断页里 `dq0=… es0=…` 之后新增三个：

| 字段 | 含义 | 想看到的值 |
| --- | --- | --- |
| `da=` | 写门铃 2 ms 后控制器自己的 EP0 dequeue | 与 `dq0` **不同** = 环被取过 |
| `do=` | 门铃写在 BAR 内的字节偏移（`DBOFF + slot*4`） | 记录用，用来核对 DBOFF 理解 |
| `e8=` | 已写进日志的事件条数 | 8 = 事件全记下了 |

`rsv=` 之后新增 `ur=<状态>/<code>`：`1` 控制器答了空环（门铃/取环/事件通道全活）、`2` 什么都没回（门铃没送到）、`3` EP0 没能建立可探状态、`0` 探针未触发。

## 日志怎么读（我这边做）

内盘 NVMe 的 GPT 空隙里：头在 LBA 64，文字从 LBA 65 起。里面会有一整套 `[USB]` 行：

```
[USB] ep0 doorbell: bar_off=… slot=… deq=…/… -> 2ms …/… (ring fetched | ring NOT fetched)
[USB] ev#1 type=… slot=… ep=… code=… p2=…
[USB] at failure: portsc=… port=… ep0deq=…/… usbsts=…
```

第一行直接回答"门铃到底有没有把控制器叫醒"；第三行给出失败瞬间的端口链路状态（PED/PLS）——那是"设备一直 NAK、控制器无限重试、于是永远没有事件"这条路的唯一证据。

## 这一版在 QEMU 上验过的

- 门铃测量方向正确：`deq=0x01c1d001 → 2ms 0x01c1d031`（前移 3 个 TRB，`(ring fetched)`）。
- 诊断页字段渲染正常：`dq0=ffffffff es0=f da=01c1d031 do=2004 e8=8 … ur=00`。
- 枚举与输入未受影响：hub/根口鼠标键盘均识别，桌面正常。
- 空环探针在 QEMU 上**必然**回 `no event`（QEMU 不产生 underrun），所以 `ur=2` 只有和 `da` 联读才有意义。

## 仍未验证

- 真机样本：`ur`、`da`、`do`、`ev#n`、`portsc` 这五项都还没有硬件读数。
- `usblog_flush` 的 flush 在输入 tick 上下文同步执行，慢介质上可能卡一下，未在硬件上量过。
- 探针会在一次失败后把该 slot 的 EP0 环"跑过一遍"，随后该 slot 被 Disable，不进入正常枚举；若某台控制器在 underrun 后停住端点并拒绝 Set TR Deq，第三次尝试可能受影响——QEMU 无法验证。
