# M8 内置系统应用（Rust 用户态）

M7 的 C++ 编译器跳过，M8 的系统应用直接用 **Rust** 编写：文件管理器、
任务管理器、设置面板、网络面板和会话管理器。它们不是内核里的函数，而是真正的 ring-3 进程 ——
用 `syscall` 取 pid、查端口、发 IPC、等事件，窗口内容通过 Novus-WM 的
显示列表提交。整个用户态运行时由 `apps/src/` 里的六个模块组成，无标准库、
无分配器、无第三方依赖。

---

## 1. 目录

```
apps/
   Cargo.toml            五个 bin + 共享库，x86_64-unknown-none
  .cargo/config.toml    目标与链接参数
  link.ld               .text 起于 0x400000，_start 在最前
  src/lib.rs            运行时入口（panic handler）
  src/sys.rs            系统调用封装（call/getpid/write/yield/ipc/exit）
  src/ipc.rs            IPC 报文格式、收发、按名字找端口
  src/wm.rs             Novus-WM 客户端：建窗、移动、显示列表、事件
  src/sinfo.rs          sysinfo 服务客户端：任务表、文件树、统计、主题色
  src/ui.rs             调色板、整数格式化、定宽文本、行/按钮
  src/devmgr/          设备管理器模块（主窗/设备树/属性窗/字段表）
  src/bin/fileman.rs    文件管理器
  src/bin/taskman.rs    任务管理器
  src/bin/settings.rs   设置面板
  src/bin/devmgmt.rs    设备管理器
```

## 2. 从源码到桌面

```
cargo build --release --target x86_64-unknown-none
        │  ELF，_start 在 0x400000
        ▼
objcopy -O binary          → out/apps/<app>.bin（扁平镜像，无 ELF 头）
        ▼
xxd -i -n k_app_<app>      → build/apps_blobs.h（C 数组）
        ▼
kernel/apps.c              → 应用表{名字, 指针, 大小}
        ▼
nuc_spawn_blob(name, blob, size, 0)  → 映射到 0x400000、64 KiB 用户栈、ring 3
```

链接脚本把 `.bss` 放在 `.rodata`/`.data` 之前，原因是 `objcopy -O binary`
不写 NOBITS 段：只有在零初始化段之后还有内容时，扁平镜像才会覆盖它的
地址范围，`nuc_spawn_blob` 的映射才不会短一截。

登录成功后 `session` 应用启动文件管理器、任务管理器、设置面板和 staged NUC；桌面顶部的任务栏（`graphics/nd_demo.c`）
再点同名按钮时 `apps_launch()` 用任务名判重，返回 `APPS_ERUNNING`，
文件管理器据此显示 “already running”。未登录时，`apps_launch()` 拒绝启动普通桌面应用。

## 3. sysinfo 服务（`kernel/sysinfo.c`）

端口名 `"sys"`，与 WM 同一个 tick 里泵消息，每次最多 8 条。列表分页，
一条应答最多 3 条记录，保证载荷不超 128 字节。

| 请求 | 载荷 | 应答 | 载荷 |
|------|------|------|------|
| 0x0301 TASKS | `{index, max, dir=0xFF}` | 0x0311 | `{total, n, rec[3]}` |
| 0x0302 FILES | `{index, max, dir}` | 0x0312 | `{total, n, rec[3]}` |
| 0x0303 STATS | — | 0x0313 | `{uptime, free_kb, tasks, windows, ipc_sent, ipc_drop, accent}` |
| 0x0304 ACCENT | `{rgb, set}` | 0x0314 | `u32` 当前主题色 |
| 0x0305 SPAWN | `{which}` | 0x0310 | `i32`（0 成功，-100 已在运行） |

`sys_task_rec_t` 32 字节：pid、ticks、exit_code、state、slice、name[14]。
`sys_file_rec_t` 32 字节：size、kind、name[24]。目录：`/apps`（内嵌应用，
可运行）、`/dev`（fb0/ps2/serial）、`/proc`（tasks/ipc/mem）。

主题色不是应用自己的状态：ACCENT 请求写的是 `ng_ctx.theme.accent`，WM 的
焦点框、标题栏高亮和 shell 的进度条都从这一处取色，所以设置面板一改，
整个桌面一起重绘。

## 4. 显示列表（WM 协议 1.1）

窗口内容不再是 7 条定长命令，而是每窗一份列表，客户端用三条消息维护：

| 请求 | 作用 |
|------|------|
| 0x010D CLEAR | 清空形状与文本列表（一帧的开始） |
| 0x010E SHAPE | 追加一个图元 `{op,x,y,w,h,color}`（填充/边框/横线/竖线/圆） |
| 0x010F TEXT | 追加一段文字 `{x,y,scale,len,color,text[96]}` |

上限 `NWM_MAX_SHAPES` 28 / `NWM_MAX_TEXTS` 40，足够一屏列表。字体是定点
5x7、步进 6px，所以对齐靠**空格补齐**（`ui::Buf::col(n)`），一行一条文本，
既省消息数也省列表槽位。

`ipc_send` 遇到队列满会返回 `EBUSY`：`wm::send` 在重试，直到 WM 把队列
腾出来，否则一次重绘（20 多条消息）会在中途断掉，留下半帧。

## 5. 应用

**文件管理器**（416x304）：三个系统目录标签和 NovusFS 磁盘视图；磁盘视图可进入子目录、
返回上级、建测试目录并执行文件写入/读取往返。`/apps` 下的条目按内核应用表顺序排列，Run 用的就是这个下标。

**任务管理器**（640x430）：进程和性能两页，支持 PID/名称/CPU 时间排序、结束任务、分页；
性能页绘制 60 点 CPU 使用历史。进程行仍显示累计 tick 与时间片。

**会话管理器**：启动时显示账号创建/登录窗口，密码掩码输入；注销结束桌面应用并返回登录，
并提供 ACPI 关机/重启。首次建号要求可写的持久 NovusFS 磁盘分区。

**设置**（720x470）：M9 起是四页的 Windows 11 设置（系统 / 个性化 / 应用 /
关于），见第 6 节。

**设备管理器**（M12，客户区 820×540）：Windows 11 设备管理器风格的双窗口应用。
主窗是菜单栏 + 工具栏 + 左侧可折叠设备树 + 状态栏；双击或右键"属性"打开一个
独立的**模态**属性子窗口（常规 / 驱动程序 / 详细信息 / 事件 / 资源 五个选项卡），
复刻 Win11 版式。数据来自新增的内核归一化设备表 `devtab` 与 sysinfo 的两条
分页请求（见第 6.1 节），入口包括桌面磁贴、任务栏图标、开始菜单与 `nsh` 直接启动。
无驱动的未知设备显示黄色 `!` 徽标与"代码 28"状态文字；更新/回退/禁用等破坏性操作
只显示说明、不做真实驱动变更。详见 `docs/设备管理器.md`。

## 6. 设置应用（M9 重做）

从 M8 的单页小面板改成 Windows 11 设置的四页结构，窗口 720×470（客户区），
左侧 168px 导航 + 右侧卡片内容 + 页脚版本号。

| 页 | 内容 | 真正作用在哪 |
|----|------|--------------|
| 系统 | 设备信息、运行时间、内存条、任务数、窗口数、IPC 收发/丢弃、当前强调色 | `sysinfo::stats`（`total_kb` 来自 `pmm_usable_pages()`） |
| 个性化 | 8 个强调色、3 套桌面背景预览、当前配色预览 | `nwm_accent_set()` / `nwm_wallpaper_set()`，改的是 `ng_ctx.theme`，一处修改全桌面重绘 |
| 应用 | 正在运行的内置应用（固定顺序：文件管理器/任务管理器/设置/设备管理器）+ pid + 状态 + 「结束」；底部「可启动」 | `sched_kill(pid)` 与 `apps_launch()` |
| 关于 | 版本、内核/用户态构成、持久化说明、里程碑 | 静态文案 |

协议新增（`kernel/sysinfo.h`，只增不改）：

| 请求 | 载荷 | 应答 |
|------|------|------|
| 0x0306 THEME | `{u8 id; u8 pad[3]; u32 value}`，id 0=强调色 1=壁纸 | 0x0315 `{u32 accent; u32 wallpaper}` |
| 0x0307 KILL | `{u64 pid}` | 0x0310 `{i32}`：0 成功 / -1 无此任务 / -2 拒绝（idle、spin）/ -3 已在退出 |

`sysinfo_stats_t` 追加 `total_kb`（真实 RAM：`pmm_usable_pages()*4`，旧口径
`pmm_total_pages()` 含 PCI 空洞，会显示成 1 TB）与 `wallpaper`。

结束任务的两段式交互：第一次点「结束」变红「确认结束」，3 秒内再点才执行，
超时自动回落。结束自己时不发请求——内核会先销毁它的收件箱，回包永远不来，
所以直接关窗 `exit`。

### 内存口径

`pmm_total_pages()` 统计的是"最高物理地址"，在 PC 上包含 PCI/MMIO 窗口，
比真实内存大两个数量级。`pmm_init()` 现在同时累计 **conventional 页数**
（`pmm_usable_pages()`），设置页的内存条用它做分母，`已用 = 总量 - 空闲`。

### 一个显示列表的坑（已修）

设置页一帧有 40+ 条图元/文本；WM 每 tick 只处理 8 条消息，于是 CLEAR 带来的
"整窗损伤"会先用**只到一半**的列表画一遍，后续图元只重绘自己的矩形——大片
空白区域永远停在半个帧上（表现为卡片下半截、页脚不出现）。新增协议
`0x0110 INVALIDATE`：客户端画完一帧后请求重绘整个客户区，WM 用完整列表合成
一次。所有多图元客户端都该在帧尾调用它。

### 设备管理器协议（M12）

设备管理器不直接扫硬件，而是读内核在启动期建好的归一化设备表 `devtab`
（`kernel/devtab.c`）：`devtab_init()` 放在 `ide_init()` 之后、`net_init()` 之前做
一次性 PCI 缓存扫描，再把块设备/网卡/显示/CPU/ACPI/USB/IOAPIC/PS2 归一化进一张
`DEV_MAX 48` 的表；`net_init()` 之后 `devtab_refresh()` 把刚探到的网卡补进去。`devtab`
对运行期 BAR 探测是安全的（不会再写 `0xFFFFFFFF` 关闭在役窗口）。

sysinfo 新增两条分页请求（复用 `sysinfo_list_t` 的 `total/index/n` 范式，每条应答 ≤128 B）：

| 请求 | 载荷 | 应答 |
|------|------|------|
| 0x031B DEVLIST | `sysinfo_list_req_t`（index/max） | 0x031C `{list_hdr; sysinfo_dev_t[3]}`：父节点下标、类/状态/类型 id、名称 |
| 0x031D DEVFIELD | `{u16 dev; u8 tab; u8 index; u32 pad}` | 0x031E `{list_hdr; sysinfo_devfield_t[2]}`：键 `DEV_F_*`、group、值 ≤56 B |

属性详情（实例路径、硬件 ID、资源范围）远超 128 B，因此按 `(dev, tab, index)`
逐条取字段，客户端缓存当前页（2 条/包、值 56 字节，长文本截断）。查询失败路径
返回 `SYSINFO_RSP_ERR`，应用退化为只显示根节点并给状态栏提示，不崩溃。

## 7. 进程退出与地址空间回收（一次真实故障的记录）

M8 上线后出现"关掉文件管理器窗口就死机"，串口停在
`[SCHED] no runnable task, halting`。根因不在应用，而在进程空间的
生命周期，四个缺陷叠在一起：

1. **空间克隆用错了模板**：`vm_space_create()` 用 `mm_get_cr3()`（"此刻
   装着的 CR3"）拷贝内核表。启动时那是内核自己的，但从 tick/syscall 里
   spawn（任务栏、`sysinfo` 的 SPAWN）时那是**当前任务**的 CR3 —— 新进程
   于是继承了父进程已经拆分过的页表，两个空间共享同一张 PT。
2. **`vm_user_map()` 无所有权检查**：共享 PT 上直接装叶子，新进程的代码页
   出现在父进程地址空间里；`free_user_leafs()` 又按"US=1 就是我的"回收，
   把别人的代码页/跳板页还给了 PMM 并清零 → idle 在 `0x90000000` 保护性
   缺页、新应用在 `0x400000` 缺页。
3. **内核栈要求物理连续**：`alloc_pages_contig(16)` 的重试每次都从同一张
   位图位置开始，第一次分配失败后永远失败，于是"第一次启动成功、之后每次
   重启都 ENOMEM"。
4. **停机点太激进**：所有任务都没了就在中断上下文里 `cpu_halt()`，时钟停
   摆，桌面冻结。

现在的规则：

* `mm_init()` 用 `mm_capture_kernel_cr3()` 存档内核 PML4，`vm_space_create()`
  只从它克隆；
* `vm_user_map()` 逐级 **写时克隆**：要写的表不在本空间 `pages[]` 里就先复制，
  并拒绝内核半区（`va >= 0x800000000000`）的映射；
* `free_user_leafs()` 只下探本空间私有的表，不再碰共享/内核表；
* `alloc_table()` 台账满 32 页即失败（不再"泄漏但继续"）；
* 内核栈改为 `g_kstacks[SCHED_MAX_TASKS]` 静态池，不再依赖连续物理页；
* 没有 READY 任务时，调度器切到内核空闲上下文（`sti; hlt` 循环），tick 继续
  驱动 WM/sysinfo，任务栏仍可启动新进程；`idle` 任务丢失会在 200 tick 内重建；
* `pmm_free_page()` 对重复释放计数并告警，`[REAP]` 行带上 `pml4=`，问题下一
  次就能从串口看出来。

回归脚本 `scripts/wm-churn.sh`（`--iso` 可对着光盘跑）会做 20 轮"关窗→任务栏
重启"，断言：无 `#PF`（除启动期 NX 探针）、无 `double free`、无
`no runnable task`、tick 持续增长、每次关窗都真的退出进程。

## 8. 验证

1. 启动日志：`[APPS] launching fileman (5552 bytes)` × 3，随后
   `[APP] fileman up` 等三行；
2. 任务管理器列出 5 个任务（idle/spin/三个应用），状态与 pid 与
   `[SCHED]` 日志一致；
3. 文件管理器 `/apps` 显示三个应用及大小，Run 已运行的显示
   “already running”；
4. 设置面板点色块，shell 进度条与所有窗口焦点框同时换色；
5. 关闭任一窗口 → WM `destroy`，任务退出；再点任务栏按钮可重新拉起；
6. 标题栏拖动、点击客户区事件、关闭按钮与 M6 一致。

## 9. M10 变更：应用表、按名字启动与安装器

M8 的应用表只有 5 项（fileman / taskman / settings / netman / session），
pps_launch(4) 与 shell 的按钮都用固定索引。M10 增加 setup 后索引会整体
后移，因此启动路径改为按名字解析：

| 变更 | 位置 |
|------|------|
| pps_launch_name(const char *name) | kernel/apps.c，未知名字返回 -1 |
| 登录闸门按名字判断 | session 与 setup 是 bootstrap，其余要求已登录 |
| setup 额外要求载荷就绪 | install_available()，普通已安装系统上不可用 |
| 内核启动 setup 后授权 | install_authorize(pid)，只允许该 pid 调 SYS_SETUP |
| sysinfo 按名字 spawn | SYSINFO_REQ_SPAWN_NAME (0x030E)，16 字节名字 |
| 应用总数 | 6（APPS_MAX），/apps 列表末尾多出 setup |

结论：新增应用不再改变任何索引的含义；旧客户端仍可调用按索引的
SYSINFO_REQ_SPAWN，但仓库内所有调用点已改用名字。
