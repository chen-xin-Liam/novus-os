# 启动顺序与启动速度规范

本篇是启动链的**规范条款**，不是经验总结。每条条款都给出：依据（哪个上游系统的哪条行为）、本仓库现状（改前是错的/是对的）、落地位置（代码点）、验证方式（时间标读数）。新增任何启动期工作时，先对照本篇判断它属于"关键路径"还是"后置阶段"，不允许两者混放。

USB 侧的启动期行为（端口上电与扫描节奏）归 `USB-xHCI驱动规范核对表.md`，本篇只引用结论，不重复条款。

---

## 0. 依据：两个上游系统怎么说

### 0.1 Ubuntu / systemd

`systemd` 的 `bootup(7)` 对启动的定义是 three 条可以照抄的行为准则：

1. **高度并行**：启动 "is highly parallelized"，服务之间除必要的少数依赖外不排序。它并没有把"顺序不确定"当缺陷，而是当成设计目标——只要**依赖关系上有限序**（bounded set of ordering constraints）成立，链条就是对的。
2. **目标链**：`sysinit.target` → `basic.target` → `multi-user.target` → `graphical.target`，每一级只等自己声明依赖的东西，不等整条链。`graphical.target` 起来时，后面还可能有服务在跑。
3. **异步拉起**：`timers.target` 由 `basic.target` **异步**拉起（`Wants=` + 不阻塞），因为它启动后才会被后面的服务用到；等它就是把一个"以后才需要"的成本放到关键路径上。

Ubuntu 桌面卡在"黑屏很久然后突然出桌面"的常见原因正是第 1/3 条被违背：某个一次性任务（网络等待、fsck、字体缓存生成）被串在 `graphical.target` 前面。反过来，Ubuntu 能在 `graphical.target` 之后继续装东西，是因为**可见的东西先出，不可见的随后**。

### 0.2 Linux 内核 `kernel/async.c`

该文件开头对异步初始化的定位是一句话：

> reduce the kernel boot time by doing various independent hardware delays and discovery operations decoupled and not strictly serialized

并明确规定对外可见的部分仍然按序：externally visible parts happen sequentially and in-order。也就是说，"并行"只允许发生在**互不依赖、且不影响外部可见顺序**的初始化之间。

### 0.3 由此得到的三条移植原则

- **P-1 关键路径最小化**：从加电到用户看到第一帧，只允许留下"后面每一步都真的依赖"的工作。
- **P-2 关键路径只依赖"发布"，不依赖"验证"**：根文件系统"能用"和"完好"是两件事；能用进关键路径，完好可以后置（代价是发现问题晚一点，而不是不能启动）。
- **P-3 诊断不是启动特性**：任何为了让开发者取证的等待（诊断页、日志刷盘、屏幕停留）都必须有**自动解除**的条件，否则它就成了所有优化上面的一层天花板。

## 1. Novus 的启动链（实测）

启动分两段：UEFI 侧（`boot/stage3`）与内核侧（`kernel/kmain.c`）。时间是 QEMU 串口里的 `[T] +Nms`（`novus_timeline()`），同一次运行内单调递增，跨段重新从 0 起算（第二段的 0 点是 `kmain start`）。

### 1.1 UEFI 侧（stage3）

改前：动画 723 ms 跑完，再花 407 ms 读盘，两段相加。

改后：读盘被切成单元，在动画的每帧空隙里推进（B-8），装载在动画结束前就读完了。

## 2. 条款

### B-1 关键路径的构成被固定为七类

- **条款**：从加电到首帧，只允许出现：时钟/TSC、GDT/IDT、物理内存与映射、堆、电源、块设备探测（AHCI/NVMe/USB）、根文件系统发布、显示初始化与首帧、调度器与会话、网络探测（仅"探测"）。
- **依据**：systemd `bootup(7)` 的目标链——每一级只等自己依赖的东西；`graphical.target` 不等 `multi-user` 之后的清理工作。
- **现状**：改前关键路径上串了 11 个自测（B-3 列出的那批），其中 `novusfs_selftest()` 因为**同时是回退根**而不可简单删除（B-2）。
- **落地**：`kernel/kmain.c` 的 `kmain()` 顺序即本条款；任何新增步骤要先在 §1.2 表里登记归属。
- **验证**：`[T] +Nms` 时间标；`first frame` 行即到达点。

### B-2 自测不得冒充根（本仓库最重要的一条）

- **条款**：`novusfs_selftest()` 不是测试。它 `ramdisk_init` + `novusfs_format` 之后把 `g_novusfs` 挂成全局回退根，而 `novusfs_root()` 在没有 live root 时正是回退到它。因此它**在有 live root 时必须移出关键路径，在无 live root 时必须留在关键路径**——留或移都不能拍脑袋，要由"boot stage 是否发布了镜像"决定。
- **依据**：P-2。根文件系统"可使用"由 live root 提供，"完好"由 Merkle 校验提供；把回退根当关键路径等于每次启动都格式化一遍自检盘。
- **现状（改前）**：无条件执行，占用 **约 1060 ms**（`filesystem selftests` 从 401 ms 到 1461 ms 的全部），是启动单点最大开销。
- **落地**：`kmain.c` 新增 `static UINT8 g_boot_have_live_root`；有 live root 时打印 `[BOOT] novusfs selftest deferred: live root published` 并交给 `boot_deferred()`，无 live root 时仍原地执行。
- **验证**：QEMU 串口出现 `novusfs selftest deferred: live root published`，且 `deferred novusfs` 在首帧之后。

### B-3 只读诊断一律后置

- **条款**：不产生"后续步骤所依赖状态"的自测，必须在首帧之后执行：`vfs_selftest`（往真实根写测试文件）、`ext4_selftest`（独立 ramdisk）、`nksym_selftest` + `nkm_selftest`、`ipc_selftest`、`nuc_selftest` + `nuc_create_spin` + `nuc_nx_probe`、`pe_selftest`、`vidmem_selftest` + `crtc_selftest`。
- **依据**：`kernel/async.c`——独立的硬件延迟与发现操作不应严格串行；对外可见部分仍按序。
- **现状**：改前全部串在关键路径上（合计约 45 ms，但 novusfs 那一条是 1060 ms）。
- **落地**：`kmain.c` 新增 `static void boot_deferred(void)`，按上述顺序执行，每步一条 `novus_timeline("deferred …")`，末尾 `[BOOT] deferred phase done`；原位保留注释说明已迁移，防止后人再加一遍。
- **验证**：`deferred *` 时间标必须**全部**晚于 `first frame`。

### B-4 后置阶段的输出不得画到桌面

- **条款**：后置阶段允许 `kputs`，但不得覆盖用户已经看到的画面。
- **依据**：systemd 的 `graphical.target` 之后服务继续输出，但不重绘桌面。
- **现状**：`graphics/nd_demo.c` 在桌面就绪时调用 `fbcon_end()`（`nd_demo.c:1865`），屏幕交给桌面合成，之后的 `kputs` 不再落到可见画面。
- **落地**：不加新机制，依赖既有 `fbcon_end()`；`boot_deferred()` 的三处调用点都在 `nd_demo_init()` 之后。
- **验证**：QEMU 截图中首帧之后没有出现文本行覆盖桌面。

### B-5 诊断页是证据通道，不是启动特性

- **条款**：45 s 的 USB 诊断页只在**日志没能写进介质**时出现（`usblog_state() != 1`）；日志已落盘时跳过并把这句话写进串口（`report page skipped: the log is on the medium`）。
- **依据**：P-3。真机没有串口，诊断页是唯一的证据通道（U-12 字段表全在那一屏），但它存在的理由是"没别的办法取证"，不是"启动流程的一部分"。条件成立时它是所有启动优化上面的天花板。
- **现状（改前）**：无条件 `nd_demo_report(rep, 45000u)`，即使日志已经写进 U 盘也照样停 45 s。
- **落地**：`kmain.c` 诊断页组装段末尾加 `usblog_state()` 判断。
- **验证**：QEMU（无 U 盘，`usblog_state()!=1`）仍出页并 `[T]` 停在其后；真机一旦 USB 面板能写日志，页自动消失——**感知启动时间的最后一道墙由 USB 修复本身解除**，不靠再调参数。

### B-6 端口扫描只在"状态变化"时等待

- **条款**：xHCI 根端口扫描里，只有本次调用**真的改变了端口状态**（刚写 PP 上电、或刚把 PLS 驱回 RxDetect）的端口才需要 CCS 去抖窗口；其余端口单次读 PORTSC 判定。
- **依据**：Linux `drivers/usb/core/hub.c` 的 `hub_power_on()` / 端口扫描——为它自己上电的端口等 `2*tg`，已有状态的端口只看一次；xHCI 侧的 CCS 反映的是连接状态，不是"读得够多次数就会变 1"。
- **现状（改前）**：每个端口无条件 `port_wait_ccs(hc, port, 40000u)`，空端口白跑 4 万次 MMIO 读；本机 12 个 USB2 口只有 5 个有设备。
- **落地**：`kernel/usb.c`——`port_power()` 与 `port_wake()` 改为返回"本次是否发生了上电/唤醒"，`usb_init()` 扫描循环只在这两者之一为真时 `port_wait_ccs()`；热插拔重扫（`usb.c:2495`）忽略返回值并在注释里写明"下一轮再看"。
- **验证**：QEMU `usb probe done` 311 → 283 ms（−28 ms，8 口 2 个活口）；端口判定结果不变（`rs=`、`at=`、`ec=` 与改前逐字一致）。

### B-7 每个阶段必须有成对的时间标

- **条款**：新增任何启动期阶段，必须在**进入**与**退出**两处各留一条 `novus_timeline()`；只在一处留等于没有归属。
- **依据**：没有时间标的阶段只能靠"总数变大了"发现，无法定位（改前 `filesystem selftests` 就是一条 1060 ms 的合成标，把 11 个自测的账算在一起）。
- **落地**：本次新增 `novusfs fallback root`、`fonts and icons`、`live root`、`mounts and sysapps`、`first frame`、`deferred *` 共 15 条。
- **验证**：`grep -E '^\[T\] \+'` 的读数可直接与 §1.2 表逐行比对。

### B-8 装载与启动动画共用一个窗口（本轮最大的 UEFI 收益）

- **条款**：动画在屏上跑的那段固定时间（这里是 7 帧 720 ms）是**已经付过的时间**，装载不能在它后面再排队；读盘被切单元，在每帧的空隙里推进，且每个单元的预算小于帧间隔，动画的落帧时间不被推迟。这与 systemd 把 `timers.target` 由 `basic.target` 异步拉起是同一条：能和一个"已经在等的时间"重叠的工作，不许把等待延长。
- **依据**：`bootup(7)` 的异步拉起；`kernel/async.c` 把独立的发现操作与可见顺序解耦。
- **现状（改前）**：`boot_anim_play()` 跑完 720 ms，才调 `stage3_load()` 再花 407 ms，两段相加（`splash anim done` +817 ms → `stage3 load done` +1144 ms）。
- **落地**：
  1. `arch/x86_64/boot/stage3.c` 把 `stage3_load()` 拆成状态机 `stage3_load_pump(budget_ms)`（`START/MERKLE/MODULES/APP/WALLPAPER/LIVE_OPEN/LIVE_SLICES/TPL_OPEN/TPL_SLICES/DONE`），至少推进一步保证不死锁；`stage3_load()` 变成"无预算跑完"，两条调度共用一台机器。
  2. 新增切片读 `slice_open()` / `slice_step()` / `slice_result()`：按 FAT 簇链的连续段读，一段一次 Block I/O，**直读进保留页**（省掉 `esp_read_reserved()` 的 pool 缓冲和一次整镜像拷贝），读满才发布 `g_live_base`——半截镜像绝不交给内核当根。
  3. `arch/x86_64/boot/main.c` 的 `boot_anim_play()` 在每帧（第 2 帧起）先 `stage3_load_pump(100u)` 再等该帧的截止时间，预算小于 120 ms 的帧间隔。
  4. 进度条跟着字节走：每读完一段 `stage_at(64 + wrote*14/size, "挂载系统镜像")`。
- **顺手修掉的真 bug**：切片读第一版把 FAT16 的簇指针按 12 位掩码截断（`0x0FFFu`），`0x1E7D` 变成 `0x0E7D`，读的是错的簇——内核立刻报 `integrity MISMATCH`，fnv 也从 `0xD5B5…` 变成 `0x99F8…`。`fat32_get()` 早把 FAT16 的 EOC（`≥0xFFF8`）归一成 `0x0FFFFFFF`，所以掩码必须保留 16 位（`0xFFFF`）、EOC 统一比 `0x0FFFFFF8`。修正后 fnv 与旧路径逐字相同（`0xD5B5548AA629063E`），`integrity PASS` 复现。
- **验证**：`[SLICE] read 8388608 bytes in 8 runs, 19ms`（改前 `[FAT] read 8388608 bytes` 走 8192 次单扇区调用、约 325 ms）；`stage3 load done` 817 ms，UEFI 侧 **−327 ms**；7 帧落点 0/121/241/361/481/601/721 与截止 0/120/240/…/720 逐帧对齐（±1 ms），看不到因为读盘而掉帧。
- **代价**：第一次 `live root` 读取期间进度条基本不动（19 ms 内读完 8 MiB），视觉上"跳到 78%"，比改动前"停 325 ms 慢慢走"更短。

### B-8c 动画末段转不确定态，不拿百分比替装载立保证（B-52）

- **条款**：进度条只允许在"进度确实可测"的区间使用。进入内核之后的装载，其剩余时间是介质速度的函数（冷介质可以是热介质的十倍），此时**必须**切成不确定态指示（沿轨滚动的短彗星），但已完成的部分要继续显示在轨上，让人看得到走到哪里。
- **做法**：`graphics/nd_boot.c` 的 `nd_boot_spin(tick)` 用同一条轨重画：轨道底色 + 暗蓝完成段（`SPLASH_BAR_TRACK_FILL`）+ 亮蓝彗星头 + 6 px 暗蓝尾，全部 `nd_round_rect` 几何，无位图、无字形、无分配。`boot_anim_play()` 在末帧之后进入"画一帧 → 给 `stage3_load_pump(8u)` 8 ms → 补齐 16 ms 帧长"的循环，装载完成即退出。
- **节奏必须由帧率掌握，不能由 I/O 掌握**：第一版把 `stage3_load_pump(20u)` 放循环头，结果一次 flash 擦除/稀疏 FAT 查找就能吞掉十几帧，慢介质上彗星直接冻住（限速 25 IOPS 时 1.6 s 只画了 5 帧）。现在的顺序是"先画、再给 I/O 一小片、再等齐帧长"：单次超预算只掉帧，不再连片冻结。
- **下限与上限**：热介质上装载在动画内就结束了，没有下限就永远看不到转圈，因此保底 4 帧（约 64 ms，UEFI 侧 <2%）；上限 240 帧只是死介质的安全阀，触顶即停画并让装载无预算跑完。
- **可验证性**：`[BA] handoff spin ticks=N` 是唯一能证明"它确实在动"的证据——QEMU 在客户机直写扫描帧缓冲期间会返回过期画面，截图只能证明画出过一帧。

### B-8b 启动期的日志载体：`usblog` 是权威，beacon 只是面包屑

- **条款**：启动阶段的日志**只能**走"内存缓冲 + 内核 `usblog` 落盘"这条链；任何"顺手往启动介质某个扇区写一行"的做法都必须先证明那块介质可写，否则宁可不写。
- **为什么**：2026-11-28 的 live ISO 在 `splash anim done` 之后立刻 `#GP` 崩机，根因是 `arch/x86_64/boot/main.c` 的 `beacon()` 往启动设备 LBA 51500 写一个扇区，而 live 启动介质是**只读光盘**——固件对只读介质照样发布 `WriteBlocks`，调用即失败并把整机带走。引导日志不能因为写日志本身而死。
- **落地**：`kernel/blkdev.c` 的 `blkdev_medium_writable()` 直接问固件的 `Media->ReadOnly`（分区视图递归问父设备），`beacon()` 只在"固件说这块介质本身可写、长度覆盖 LBA 51500"时写；分区化的 ESP 与光盘一律跳过并打一行 `boot beacon: no writable boot medium, no sector log`。**不要**为了写 beacon 去"另找一块能写的盘"：第一版那样做时挑中了一个表里报满长度、实际只有自己分区窗口的设备，桌面镜像当场复现同形状 `#GP`（`RDX=0xC92C`）。
- **布局**：内核日志 `usblog` 在 LBA 51200（头扇区）+ 51201…51455（正文 255 扇区，遇全零结束）；beacon 的 51500 在它之外，两者不重叠。真机回读脚本读的是内盘 NVMe 的 GPT 间隙（LBA 64 头 + 65 起正文），与 U 盘上的 `usblog` 是两套独立载体。
- **验证**：同一 ISO 修完再引导 → 一行跳过提示之后正常 `stage3 load done` → `kmain start` → 首帧；桌面镜像同样正常。

### B-9 Merkle 校验**不能**后置（实测否决）

- **条款**：live root 的 `novusfs_merkle_verify()` 必须留在挂载之后、任何写入之前，不得挪进 `boot_deferred()`。
- **依据（实测）**：先按"结论只是告警、可以后置"的假设把它搬进后置阶段，真机之外的第一轮 QEMU 就给出 `[M3] live root integrity NOT BUILT`——不是 PASS 也不是 MISMATCH。原因是 `novusfs_merkle_invalidate()` 在任何一次写入时清 `sb.merkle_valid`，而挂载和首帧之间正好有 `sysapps_seed()` / `mountcfg_apply()` 的写入。根一旦被写过，已保存的 root 就失去意义，后置校验只剩下"重建一棵新树再和自己比"的空转。
- **现状**：`live root mounted` +368 → `live root verified` +640，**全树重建 272 ms**（2048 个 4 KiB 块，每块一次读 + 一次 `novus_rs_sha256`），是全内核单点最大项，但它是"根可用之前"的检查，与 B-2 的"回退根自测"性质不同：后者不产生任何依赖，前者确认了 root 身份。
- **落地**：`kmain.c` 里校验保持在 `novusfs_mount()` 之后、字体/图标缓存与所有写入之前，只是新增 `live root mounted` / `live root verified` 两个标把 1 ms 挂载、272 ms 校验、64 ms 字体缓存分开记账。
- **将来若要省掉它**：只能改 `novusfs` 本身（例如把"写入即失效"改成增量更新树、或对只读 live root 跳过 invalidate），不是启动顺序问题。

### B-10 deferred 阶段放进调度器：本轮做不到

- **条款（目标）**：`boot_deferred()` 应该作为调度器里的一个低优先级任务跑，而不是在 `sched_start()` 之前同步跑完，这样首帧之后的那 1058 ms 里输入已经能被处理。
- **依据**：Linux 的 async probe 最终由 kthread 执行，systemd 的单元也由 PID 1 在事件循环里按依赖调度，都不是"启动函数里同步跑完"。
- **现状（为什么没做）**：`kernel/sched.c` 只有用户态任务入口（`sched_create_user` / `sched_create_user_ex`，需要 `vm_space_t`），没有内核线程的创建原语；`sched_start()` 直接切到既有的用户任务集合。加一条"内核态任务"路径要动调度器的栈与切换、以及这些自测对全局状态的假设（`novusfs_selftest()` 会格式化并挂回退根，`nuc_create_spin()` 会起用户任务），不是启动顺序的改动，是调度器的新能力建设。本轮**明确未做**，把这 1058 ms 的输入延迟如实记在这里。

### B-11 仍然没动的部分（候选，不是"已优化"）

- **启动动画固定 723 ms**（`[BA] frame n/7`，7 帧、末帧 720 ms 交棒，`splash anim done` 817 ms）。它不依赖任何初始化，现在是装载的"遮罩"，所以它本身已经是 UEFI 侧的关键路径——要么缩短（产品决定），要么把内核侧的前几段也塞进这个窗口（改动更大，本轮未做）。
- **桌面绘制 365 ms**（`demo init start` +909 → `first frame` +1274）：壁纸解码 + 图标 + 首次 present 合成。这是内核侧现在最大的一块，未拆细。
- **Merkle 272 ms**：见 B-9，属 `novusfs` 的哈希性能问题（8 MiB / 272 ms ≈ 30 MB/s，远低于 SHA-256 软件实现常见水平），不是启动顺序问题。
- **USB 探测 ~90 ms**（`power storage probes` +194 → `usb probe done` +277）：真机 12 口 5 活口，收益比 QEMU 大，但需要真机时间标。

### B-12 控制器初始化与端口枚举分离（USB 不在启动关键路径）

- **条款**：`usb_init()` 只允许做控制器级初始化（HCRST、命令/事件环、DCBAA、ERST、interrupter）加**每个端口一次 PORTSC 快照**；每口的复位、描述符走查与两次重试属于"设备枚举"，只能在首帧之后由 `usb_hub_probe_all()` 执行（无桌面分支例外：那条路径没有首帧，枚举在 shell 启动前跑完）。运行期的插拔只在 `PORTSC.CSC`（bit 17，RW1C）置位时动作，不许周期性地把所有端口复位一遍。
- **依据**：Linux `xhci_pci_probe()` 复位并启动控制器、注册根 hub 就返回，设备枚举发生在 `hub_event`（workqueue），只针对有变化位的端口；Windows 也把这段交给 hub 驱动 worker。启动路径上只要出现"每设备重试 + 100 ms 等待"，一个坏端口就能决定首帧时间——而坏端口正是这台机器上的常态（`cn=5` 里四口停在 step 3）。
- **现状（改前）**：`usb_init()` 同步跑完所有控制器所有端口，QEMU 68 ms（`nvme probe done` 193 → `usb probe done` 261），真机 12 口 5 活口只会更多（B-11 里记的候选项）。
- **落地**：`kernel/usb.c` 新增 `hub_port_probe()`（原循环体单口化）与 `usb_hub_probe_all()`（`usb.h` 导出、`g_hub_done` 幂等），`usb_init()` 的端口循环删除并记录 `hc->rep`；`kernel/kmain.c` 的 `boot_deferred()` 开头与无桌面分支各调用一次，并在其后 `usblog_retry()` 重选日志介质（U-39）。
- **验证**：QEMU `nvme probe done → usb probe done` **68 → 21–24 ms**，`usb hub done` 落在首帧之后 46–51 ms；设备判定 `at=00009900`、`evs=02/06/0c`、`dw1=00050000`、`dw1`/`td0` 与基线逐字不变；注入鼠标后 `[USB] xhci HID report addr=1 bytes=4` 到达、光标落点一致。
- **未做**：仍是轮询而不是中断驱动（xHCI 中断未接，U-13 同款）；真正并行需要内核线程/workqueue，本内核没有第二个上下文（与 B-10 同一条约束）；真机时间标仍缺。
- **补充条款（2026-11-25，U-41）：端口遍历必须有调用方给的时间预算。** 上面这条只规定了"不在关键路径"，但没说它跑起来能花多久：`usb_hub_probe_all()` 一口气跑完所有端口，每个请求 1000 ms 预算，QEMU 上 8 个 hub 端口就把 `usb hub done` 推到首帧后 **+8130 ms**。现在 `usb_hub_step(budget_ms)` 用静态游标一次推进一个端口、`hub_walk()` 自带 500 ms 截止；`boot_deferred()` 只给 700 ms，剩下的由 `usb_hid_poll()` 每 tick 40 ms 接着走，走完再 `usblog_retry()`。实测 port 段：hub 场景 `+2229 → +2291`（62 ms）、根端口场景 `+2164 → +2217`（53 ms）。因此"首帧之后的后置阶段"多了一条硬边界：任何后台遍历的时间上限由调用方给，不许由设备数乘最坏等待决定。未做：续跑挂在输入 tick 上，报告页期间不推进。
- **补充条款（2026-11-26，U-48）：预算限制的是"卡住的时间"，不是"设备是否活着"。** 上一版把端口遍历里每个控制请求压到 150 ms，用来保证首帧不被拖住；但 Linux 给一个已枚举端口上的控制请求 5 s（设备一直 NAK 就继续等），把预算压到 150 ms 会让"200 ms 才答的设备"和"从不回应"在页面上完全同形（都记成 `ec=T`），而这两种情况的处置完全不同。现在预算由调用方按场景给：`boot_deferred()` 用 `USB_WAIT_MS`（1000 ms），`usb_hid_poll()` 续跑时用 250 ms（一次输入 tick 的可见卡顿上限），遍历自身的时间预算（B-12 的 700/40 ms）不变。代价是"彻底不回应"的端口最坏要花约 6 s（三遍 bring-up × 两遍控制请求 × 1000 ms），只发生在坏端口上，且被调用方的时间预算摊到多个 tick。
- **补充条款（2026-11-26，U-50）：写 framebuffer 的页面退出后必须整屏重绘一次。** 诊断页（`nd_demo_report()`）是直接写 framebuffer 再 `nd_present(全屏)`，窗口管理器看不到这块像素、damage 集合里也没有它；页面退出后桌面只重绘自己认为脏的区域，留在屏幕上的就是"边框在、内容区纯白"。凡是绕过 WM 直写的页面，退出时都要调 `nwm_repaint_all()` 广播一次全屏 damage——这不是性能问题，正确性优先。实测 QEMU 日志里该行出现在报告页 dump 之后、桌面首帧之前。

## 3. 测量方法（可复现）

1. 构建：`cmd /c C:\msys64\tmp\build_main.cmd`，日志 `C:\msys64\tmp\m130.log`，检查 `exit=` 与 `warning:`。
2. QEMU 起镜像（`rq113.sh` 系）并抓串口到 `sxNNN.log`。
3. `grep -E '^\[T\] \+' /tmp/sxNNN.log | sed -e 's/\r//' | awk '!seen[$0]++'` 去重后按时间标排序阅读；UEFI 段与内核段各从 0 起算。
4. 同一时间标的两次读数即可做"改前/改后"对照；不同时间标之间只能看区间。

## 5. 尚未闭环

- 真机（HP EliteBook 640 G10）无串口，`C:\msys64\tmp\usblog.txt` 仍为 0 字节，真机的三段耗时（UEFI 侧、内核侧、诊断页）**全部没有数字**；本页所有读数来自 QEMU，TSC 频率与磁盘速度与真机不同，比例可信、绝对值不可直接外推。
- B-5 的后果未验：真机上 `usblog_state()==1` 从未成立过，所以"日志落盘就跳过诊断页"这条只在代码里成立，还没被真实启动走过。
- B-6 在真机上的收益未测：真机 12 个 USB2 口（`fw=5` 说明固件见过 5 个设备），空口越多收益越大，但一轮 MMIO 读的代价在真机（PCIe 后端的 PCH）上比 QEMU 高，需要真机时间标才能定量。
- B-11 的四项都还是候选，没有动手（动画 723 ms、桌面绘制 365 ms、Merkle 272 ms、USB 90 ms）。
- 真机上的**磁盘速度**是本轮最大的未知：QEMU 里 8 MiB / 19 ms ≈ 440 MB/s，真机 U 盘 FAT16 + 单扇区固件很可能仍是几十 MB/s，切片读的收益（8 次调用 vs 8192 次）会更大，绝对时间会更长。
